# 设计取舍 / Design decisions

| 决定 | 理由 |
|---|---|
| 装「流程」不装「结论」 | 结论会过期、口径会漂移、读者也无从核验；流程可以复用，且每一步的判据都写在包里。结论由执行者按流程跑出来，责任与依据都清楚 |
| 事实层冻结、文风另做一道末位工序 | 把「表达」和「事实」放在同一步，就会出现「顺手改个数」——所以事实层（数字／口径／结论方向／脚注）在文风阶段明令不动，并出 `style-report.json` 自证 |
| 门禁必须能被证伪 | 一道从没在坏件上失败过的门禁，和一道永远返回 PASS 的死门禁，观察起来完全一样。所以每道判据都要配注入式负向对照，少一个就拦发布 |
| 「0 problems」必须声明范围 | 不说清查了什么，等于让读者以为「全查过了」。`CRITERIA.md` 逐条写明「不查什么」，把盲区摆在明面上 |
| 改名必须同批完成 | 方法包改名会波及 skill-packages／experts／本体／SKILL.md／三份文档十处引用；漏改一处就是悬空引用。所以用工具同步，且用 `ref-integrity` 判据兜底 |
| 禁例词干阈值设为 0 | 源一多，禁例表就容易落后于账本。阈值一旦允许「缺口存在」，它就会一直存在。设为 0 ⇒ 新增源**强制**同步禁例表 |
| 闸门 C 声明为 semantic，不假装可执行 | 包里没有独立执行器去查「数据有没有断点」。把它写成 deterministic 是撒谎；写成 semantic 并附 `wiring.reason` 才是诚实的做法 |
| 「未获取」要写进正文，不能留空 | 报告生成器若不自带空值自检，`None/nan/inf` 会一路进正文——而数字一致性门禁只核对数字，抓不到 `None` |
| 只用一层抽象：一个 `pack.json` + 十个维度目录 | 十维度是 Expert Profile v2 的既定契约。多一层封装就得维护两套版本号，而版本漂移是这个包最怕的病 |
| 版本用一条命令 bump，digest 自动重钉 | SHA-256 对行尾敏感，改 `SKILL.md` 的 frontmatter 就会改它自己的摘要。手改必错，所以交给 `bump-version.mjs` |
| `.gitattributes` 钉 `eol=lf` | 不钉行尾，Windows 上 checkout 就让全部 digest 错位，而 digest 是这个包可复现性的地基 |
| 知识源只发布「内化摘要层」 | 原著与教材版权归原作者与出版方。发布提炼与方法框架、逐条登记来源、不发一个字的原文——这条线是可辩护的，前提是它写清楚（见 `spec/provenance.md`） |
| 发布前十件套全绿才发布，且 CI 也跑 | 纪律不能只靠人记得。把「十件套」写进 CI，纪律就成了仓库的一部分而不是某个人的习惯 |
| 保留历史版本记录不改写 | v2.3.0 那条写「38 源」在当时是真的。改写历史会让版本历史失去「当时发生了什么」的价值 |
| 英文版只做摘要，不做全文对译 | 维护两份全文必然漂移；英文版只保证「能看懂这个包能干什么、去哪找」 |
| AI 入口页（`AGENTS.md`）排在 README 之前 | 拿到包的人多数是 AI 助手，不是人。`AGENTS.md` 先讲「你是谁、别做什么、三道闸门为什么不能跳」，再讲文件在哪 |
| `llms.txt` 单独一份 | 给 AI 的索引与给人的 README 用途不同：前者要的是「有哪些文件、各自干什么」，后者要的是「这东西有什么用」 |
| 保留 MIT，不改 Apache | 源包是 MIT，新仓库沿用，避免同一份内容出现两套授权表述 |
