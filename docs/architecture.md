# 架构 / Architecture

这份文档回答一个问题：**这个包为什么长成这样，以及改一处会波及哪里。**

## 一句话

`macro-capital-ch` 是一个 Expert Profile v2 领域包：它不装结论，装**产生结论的流程**，
并且给这个流程配了一套可机检的纪律。

## 三个层次

```
┌─────────────────────────────────────────────────────────────┐
│  ① 方法层  method-packs/ + skills/                          │
│     十五层能力框架 · 三道横切闸门 · 六步内化流程             │
│     skill-packages/ 声明本包引用了哪些方法包                  │
├─────────────────────────────────────────────────────────────┤
│  ② 执行层  scenarios/ + team-templates/ + output-templates/  │
│     任务 DAG · 槽位与产物落点 · 版式契约（tokens/组件/指令）    │
│     experts/ 给出执行者的能力与否决规则                       │
├─────────────────────────────────────────────────────────────┤
│  ③ 纪律层  quality-policies/ + scripts/ + CRITERIA.md        │
│     15 道门禁（含可机检 config）· 十件套发布前检查              │
│     负向对照证明每道门禁抓得住自己的缺陷                       │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向是单向的**：纪律层不认识执行层，执行层不认识方法层的方法内容，
但三者通过 `id` 互相引用。**这正是「改名会波及全场」的原因**——也是为什么改名必须同批完成。

## 一次改动的波及面

以「给方法加一层」为例（本包 v2.9.0 正是这么做的）：

| 要改的地方 | 为什么必须一起改 |
|---|---|
| `method-packs/fifteen-layer-framework.json` | 层定义本体 |
| `skill-packages/macro-capital-framework.json` → `contributions.methodPacks` | 否则该方法包「不被本包引用」 |
| `experts/*.json` → 方法引用与描述 | 否则专家 Profile 与方法层脱节 |
| `domain-knowledge/*.json` → 实体与关系 | 否则本体里查不到新层 |
| `skills/.../SKILL.md` → 模板引用、验收标准、闸门正文 | 否则执行者读到的是旧规则 |
| `README.md` / `README.en.md` / `SUBMISSION-CHECKLIST.md` | 否则三处版本与结构描述漂移 |
| `quality-policies/baseline.json` → 新增门禁 + 绑定 | 否则新门禁 unbound（跑不到）或纸门（没 config） |
| `scripts/selftest-gates.mjs` → 新判据的负向对照 | 否则新判据「从没在坏件上失败过」 |
| `source/SOURCE-MANIFEST.json` → 若新增知识源 | 否则源账本与禁例表脱节 |

`check-pack.mjs` 的 `ref-integrity` 判据会当场拦下漏改的引用点；
`doc-version-drift` 拦下版本三处不同步；`negative-control-gap` 拦下「改了判据却没配对照」。

## 一次产出的完整链路

```
   skill_version 绑定
          ↓
  ┌───────────────┐
  │ 取数          │  Wind CLI → westock → 公开接口自算 → 外部口径
  │ （记档位）    │  当期落在哪一档必须写进方法可靠性声明
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ 数据质检三件套│  闸门 C①：断点检测 · 复权校验 · 跨源对账
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ 六步研判      │  钱从哪来 → 钱变利润 → 价格装多少预期
  │               │  → 结构定价自洽 → 周期定位风险归属 → 错了会怎样
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ E[R_A] 分解   │  ① 支付收益率 ② 现金流增长 ③ 估值回归
  │ （③ 的两版并列）│  只有两版同号才可建仓
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ 三道闸门      │  A 统计可信（七条）· B 成本可执行（六条）
  │               │  C 数据质量与规则版本（四条）
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ 数字三处对撞  │  摘要 = 正文 = 底座
  └───────┬───────┘
          ↓
  ┌───────────────┐
  │ 文风渲染      │  末位工序 · 事实层冻结 · 出 style-report.json
  └───────┬───────┘
          ↓
        产物
```

**注意两道容易被跳过的检查**：闸门 C 的质检三件套在取数之后、研判之前；
文风渲染在最后。如果跳过前者，后面所有数字都建在未验证的数据上；
如果跳过后者，产物虽然对，但表达不达发布标准。

## 三个刻意设计的「不信任」

这个包对**自己**也设了检查，这不是修辞，是三个具体机制：

1. **负向对照（`selftest-gates.mjs`）**——往包里注入已知缺陷，断言对应判据真的报错。
   一道从没在坏件上失败过的门禁，和一道永远返回 PASS 的死门禁，观察起来完全一样。
2. **判据登记表（`CRITERIA.md`）**——逐条写明「查什么／不查什么／能报什么 code」。
   「0 problems」因此有明确范围，而不是一个无边界的安慰。
3. **门禁接线检查（`check-gate-wiring.mjs`）**——每道有 `config` 的门必须声明
   `wiring`，指明哪个执行器消费哪些键。声明被加载 ≠ 声明生效，
   这个包在一天内连踩三例同类问题，所以把它变成了事前可机检。

## 想改点什么，先看哪

| 你想改 | 先读 |
|---|---|
| 加一层能力 / 加一道闸门 | `spec/contracts.md` §「一次改动的波及面」在 [README](../README.md) 的方法包章节；照 v2.9.0 的做法抄 |
| 加一个知识源 | [spec/provenance.md](../spec/provenance.md) §「Adding a source」 |
| 改输出版式 | `output-templates/*.json` 的 `designSystem`；改完必须跑 `check-template-conformance` |
| 改门禁判据 | `scripts/check-pack.mjs` 顶部的判据表 → 改完必须重生成 `CRITERIA.md` **并补负向对照** |
| 只想用它 | [AGENTS.md](../AGENTS.md) |
